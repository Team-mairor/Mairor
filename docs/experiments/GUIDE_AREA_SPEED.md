# 가이드 영역 생성 속도·메모리 줄이기

2026-11-08 · S15P31A306-333

가이드 영역 작업은 BE가 넘긴 사진을 받아 얼굴 점을 찾고, 사진을 판정한 뒤, 단계마다 직전·직후 사진을 얼굴 지도에 펴서 바른 곳을 찾는다. 이 작업이 어디에 시간과 메모리를 쓰는지 재고, 결과(`guide_area.json`)를 한 바이트도 바꾸지 않으면서 줄였다. 시도한 방법, 고른 것과 고르지 않은 것, 그 근거 숫자를 남긴다.

## 요약

- 운영 AI 서버(2코어)처럼 코어 2개로 묶어 잰 값으로, 31분 시험 영상은 **13분 32초 → 5분 45초(−58%)**, 9분 영상은 **3분 55초 → 1분 39초(−58%)**다. 최대 메모리는 4.3GB → 3.3GB다.
- 두 영상 모두, 모든 측정에서 결과 파일이 줄이기 전과 바이트까지 같다.
- 바꾼 것은 세 가지다. ① 영역에 쓰는 사진만 받는다(6,477 → 1,376장). ② 같은 사진을 얼굴 지도에 한 번만 편다. ③ 가림 찾기·OpenCV 일꾼(스레드)을 1명씩 두고, 단계를 두 줄로 나눠 동시에 만든다.
- 단계별로 끝난 영역을 먼저 보내는 방식, 프로세스 두 개로 나누는 방식은 하지 않았다.
- 서버 흉내로 잰 값이다. 운영 서버에서 실제 요청으로 잰 값은 아직 없다.

## 재는 방법

### 도구

[`ai/tools/profile_guide_area.py`](../../ai/tools/profile_guide_area.py)는 서비스 입구(`area_work.build_area_from_frames`)를 그대로 부른다. 사진은 이 컴퓨터에서만 열리는 임시 웹 서버로 내주어 BE 요청처럼 주소로 받게 한다. 서비스 코드는 고치지 않고, 구간 함수들을 시계로 감싼 판으로 잠깐 바꿔 끼운다.

- 구간마다 「안쪽 포함 시간」과 「자체 시간」을 따로 센다. 자체 시간을 모두 더하면 큰 구간 시간과 같다.
- 사진 읽기·얼굴 지도 펴기·가림 찾기는 호출 수와 서로 다른 사진 수를 같이 센다. 반복이 숫자로 보인다.
- 메모리는 0.2초마다 프로세스 전체 사용량(윈도우 작업 집합)을 재서 구간별 최대값을 남긴다. MediaPipe·onnxruntime이 잡은 메모리도 들어간다.
- `--cores`로 코어 수, `--ort-threads`·`--cv-threads`로 가림 찾기 모델과 OpenCV 일꾼 수, `--lines`로 영역 만들기 줄 수를 정한다.
- 결과 `guide_area.json`과 구간 기록 `profile.json`을 남긴다.

## 영역에 쓰는 사진만 받기

### 고르는 규칙

부위 분석은 단계 직전 창과 직후 창 사진만 쓴다. 창 길이는 부위마다 다르다.

| 부위 | 직전 창 | 직후 창 |
| --- | --- | --- |
| 블러셔 | 1초 | 1초 |
| 눈썹 | 1초 | 2초 |
| 아이섀도 | 2초 | 1초 |
| 아이라인 | 1초 | 3초 |
| 립 | 없음 | 1초 |

사진 판정은 얼굴 크기를 앞뒤 1초 사진들의 가운데 값과 견준다. 창 끝 사진도 모든 사진으로 판정할 때와 같게 하려고 창 양쪽에 1초씩 더했다. 분석하지 않는 단계(파운데이션·쉐딩·하이라이트·마스카라·기타)는 사진을 고르지 않는다.

받기 전에 이 규칙으로 고르고([`reference_area.needed_frames`](../../ai/app/tasks/area/reference_area.py)), 고른 사진만 받고 얼굴 점과 판정을 돌린다.

## 같은 사진을 얼굴 지도에 한 번만 펴기

### 시도한 방법

부위 다섯 개는 모두 한 곳(`area_preparation.rows_to_known_map`)에서 사진을 읽고 편다. 여기에 「한 번 편 지도를 기억해 두기」를 붙였다. 기억 상자를 넘기는 방법을 셋 견줬다.

| 방법 | 장점 | 단점 | 고름 |
| --- | --- | --- | --- |
| 부위·빌더 함수 인자를 「사진 → 펴진 지도」 함수로 바꿈 | 가장 분명하다 | 부위 5개·빌더·지표 도구·시험까지 고칠 파일이 많고, 같은 파일을 고치는 다른 작업과 겹친다 | |
| **`load_photo` 자리에 사진 꾸러미(`RememberedPhotos`)를 넘김** | 고칠 파일 2개. 꾸러미가 인자로 보인다. 그냥 함수를 넘기면 지금처럼 매번 편다 | 「꾸러미면 기억을 쓴다」는 규칙이 함수 안에 있다 → 독스트링에 적음 | ✓ |
| 작업하는 동안만 켜지는 문맥 변수(`ContextVar`) | 인자가 그대로다 | 인자 어디에도 안 보이는 전역 상태라 찾기 어렵다 | |

### 기억할 장 수

사진 한 장의 지도(3MB)와 가린 칸 지도(1MB)를 합쳐 약 4MB다. 같은 사진을 다시 쓰는 것은 같은 단계의 왼쪽·오른쪽이 바로 이어서 쓸 때다. 그래서 한 단계 분량만 담으면 된다.

| 후보 | 최대 메모리 | 판단 |
| --- | --- | --- |
| 32장 | 약 128MB | 창이 긴 단계에서 왼쪽 사진이 오른쪽 차례 전에 밀려날 수 있다 |
| **64장** | 약 256MB | 시험 영상 한 단계 창 안 사진은 가장 많을 때 40장(아이라인), 평균 27.4장이다. 가림 찾기 기억(`OCCLUSION_KEEP`)과 같은 수다 |
| 전부(552장) | 약 2.2GB | 효과는 64장과 거의 같고 메모리만 크다 |

기억한 지도는 읽기 전용으로 잠가, 꺼내 쓰는 쪽이 고치면 오류가 난다.

### 지도 펴기 자체

지도 펴기는 1080p 사진 전체를 소수로 바꾼 뒤 필요한 칸을 집었다. 필요한 픽셀을 먼저 집고 무게와 곱할 때 소수가 되게 바꿨다. 정수는 소수로 바뀌어도 값이 같아 결과가 같다. 실제 사진 20장으로 견줬다.

| 판 | 지도 펴기 한 번 | 고름 |
| --- | --- | --- |
| 처음 | 195.0ms | |
| **필요한 픽셀만 소수로** | 179.1ms (−8%) | ✓ 한 줄이 줄어 더 단순하다 |
| 픽셀을 한 줄로 펴서 한꺼번에 집기(`np.take`) | 픽셀 섞기만 −20% | 영역 전체로 몇 초라 도우미 함수를 늘릴 만하지 않다 |

한 번 펴는 시간 184ms 중 138ms가 68만 칸 × 3색의 소수 계산이라, 사진 전체를 소수로 바꾸는 일은 생각보다 작았다.

## 일꾼 수와 두 줄

### 서버를 흉내 내는 방법

| 방법 | 결과 | 고름 |
| --- | --- | --- |
| 코어 2개로 묶기만 | onnxruntime·OpenCV가 22코어를 보고 일꾼을 많이 만들어 코어 2개를 다툰다. 작은 입력에서 가림 찾기가 사진 한 장에 0.08초 → 2.1초로 25배 느려졌다. 서버는 처음부터 코어 2개를 보므로 이렇게 되지 않는다 | |
| Docker 컨테이너를 CPU 2개로 | 컨테이너 안에서도 라이브러리가 PC 전체 코어를 볼 수 있어 같은 문제가 남을 수 있다 | |
| **코어 2개로 묶고 일꾼 수를 서버 값으로 정함** | 다툼 없이 서버와 비슷한 조건 | ✓ |

MediaPipe(얼굴 점)는 파이썬에서 일꾼 수를 정하는 칸이 없다. 코어 2개로 묶어도 느려지지 않아 다툼은 없다.

이 컴퓨터의 0·1번 코어는 빠른 코어라, 일꾼 1명이 하는 일(지도 펴기)은 22코어로 풀었을 때보다 오히려 빨랐다(137.9 → 95.1초). 서버 코어 하나가 이만큼 빠르다는 보장은 없어서 서버 흉내 숫자는 같은 조건 안에서 견주는 데 쓴다.

| 가림 찾기 | OpenCV | 전체 | 영역 | 가림 찾기 | 지도 펴기 | 부위 찾기 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 2 | 403.3초 | 339.3초 | 127.4초 | 95.1초 | 76.9초 |
| 2 | 2 | 448.2초 | 381.3초 | 138.7초 | 116.7초 | 77.0초 |
| **1** | **1** | **392.1초** | **329.2초** | 125.0초 | 93.6초 | 71.5초 |

- 가림 찾기 일꾼 2명은 확실히 느리다(전체 +11~16%). 물리 코어 하나를 둘로 나눈 코어에서 계산을 나누고 합치는 수고가 더 크고, 그 일꾼이 지도 펴기의 코어까지 붙잡는다.
- OpenCV 일꾼 1명은 흐리기를 쓰는 부위 찾기가 두 경우 모두 5초쯤 줄었다. 전체로는 3% 안쪽이다.
- 서버의 onnxruntime 기본값은 물리 코어 수라 1명일 것으로 보지만, 서버 사양에 따라 2명을 고를 수도 있다. 그러면 위처럼 10% 넘게 느려지므로 설정값으로 1명을 정했다.

### 단계를 두 줄로

남은 영역 시간의 대부분(지도 펴기·부위 찾기)은 코어 하나만 쓴다. 단계를 두 묶음으로 나눠 스레드 두 개로 동시에 만들고, 단계 순서대로 합쳤다.

- 아이라인은 앞 아이라인 단계에서 안내한 칸을 이어받으므로 모두 첫 줄에 순서대로 둔다.
- 나머지 분석 단계는 창 안 사진이 많은 것부터 사진 수가 적은 줄에 넣는다. 사진 수가 시간과 거의 비례한다. 시험 영상은 10단계·25단계, 사진 320장·310장으로 나뉘었다.
- 줄마다 지도 꾸러미와 가림 기억을 따로 둔다. 같이 쓰면 두 줄이 넣고 빼다 꼬일 수 있다.

| 방법 | 장점 | 단점 | 고름 |
| --- | --- | --- | --- |
| **스레드 두 줄** | 메모리가 조금만 늘어난다 | 파이썬은 한 번에 한 스레드만 파이썬 코드를 돌려(GIL), numpy·OpenCV 안에서 도는 만큼만 겹친다 | ✓ 먼저 재 보고 10% 넘으면 넣기로 함 |
| 프로세스 두 개 | 진짜로 동시에 돈다 | 모델과 얼굴 점 결과를 따로 들어 메모리가 거의 2배(3GB → 6GB대, 컨테이너 상한 7G)다. 서버 코어가 물리 코어 1개라 얻는 것도 크지 않다 | |
| 나누지 않음 | 바뀌는 것 없음 | | |

서버 흉내 조건(가림 1·OpenCV 1)이다.

| | 한 줄 | 두 줄 |
| --- | --- | --- |
| 영역 만들기 | 336.3초 | 275.4초 (−18%) |
| 전체 | 401.4초 | 339.7초 (−15%) |
| 최대 메모리 | 3,032MB | 3,229MB |
| 결과 | 기준 | 바이트까지 같음 |

두 줄에서 가림 찾기 한 장은 0.23초 → 0.39초로 늘었다. 두 줄이 물리 코어 하나를 나눠 쓰기 때문이다. 그래도 동시에 돌아 전체 시간이 줄었다. 기준(10%)을 넘어 넣었다.

### 서비스 설정

`ai/app/core/config.py`·`ai/.env.example`에 세 칸을 두었다. 서버 코어 수가 바뀌면 `.env`로 맞춘다.

| 설정 | 기본값 | 적용 |
| --- | --- | --- |
| `AREA_LINES` | 2 | 영역 작업 하나 안에서 단계를 나눌 줄 수 |
| `AREA_ONNX_THREADS` | 1 | 서버가 켜질 때 가림 찾기 모델을 이 일꾼 수로 연다 |
| `AREA_OPENCV_THREADS` | 1 | 서버가 켜질 때 `cv2.setNumThreads` |

일꾼 수는 서버가 켜질 때(`main.lifespan`)만 정한다. 개발 PC의 지표 도구와 시험은 지금처럼 코어를 다 쓴다.

## 하지 않은 것

| 검토한 것 | 하지 않은 이유 |
| --- | --- |
| 끝난 단계부터 영역을 먼저 보내기 | 영역 만들기가 31분 영상에서 약 6분으로 줄었고, 그동안 진행 알림이 1초마다 간다. 먼저 보내려면 콜백 형식·BE 저장·FE 표시를 모두 바꿔야 해서 얻는 것에 비해 비용이 크다 |
| 프로세스 두 개로 나누기 | 메모리가 거의 2배가 되어 컨테이너 상한에 가깝고, 서버 코어가 물리 코어 하나라 얻는 것도 크지 않다 |
| 지도 펴기를 `np.take`로 | 영역 전체로 몇 초다 |

참고로 AI는 이제 BE가 보낸 사진 중 일부만 받는다(31분 영상 6,477장 중 1,376장). BE가 사진을 다른 데 쓰지 않는다면, 같은 규칙으로 그 사진만 뽑아 올려도 된다.

## 다시 재는 방법
