# 지표 도구 속도 올리기

2026-11-09 · S15P31A306-334

가이드 영역을 재는 지표 도구 넷(잡음 `noise_metric.py`, 안정성 `stability_metric.py`, 색 변화 `timing_metric.py`, 경계 `boundary_metric.py`)과 판정 도구(`guide_scorecard.py`)를, 결과 파일을 한 바이트도 바꾸지 않으면서 빠르게 했다. 부위별 기준값 자동 튜닝(S15P31A306-343)과 모델 평가(S15P31A306-347)에서 이 도구들을 기준값만 바꿔 수십 번 다시 돌리기 위해서다. 어디에 시간이 들었는지, 시도한 방법과 고른 것·고르지 않은 것, 그 근거 숫자를 남긴다.

## 요약

- 시험 영상 전체(6,477장)를 도구 넷과 판정 도구로 재는 시간이 **2시간 18분 13초 → 첫 실행 14분 44초(−89%), 다음 실행 6분 54초(−95%)**다. 기준값 하나를 바꿔 다시 재는 시간은 **6분 16초**다.
- 모든 측정에서 결과 파일 다섯 개가 빠르게 하기 전과 바이트까지 같다. 기준값을 바꾼 다시 재기는 바꾼 부위의 줄만 달라진다.
- 바꾼 것은 넷이다. ① 같은 사진을 얼굴 지도에 한 번만 편다(서비스 `RememberedPhotos`를 도구에 연결). ② 편 사진 지도와 사진 묶음의 대표 지도를 디스크에 저장해 도구끼리·다음 실행이 꺼내 쓴다. ③ 기준값만 바꿔 다시 재는 빠른 판(`--set`·`--tag`)을 둔다. ④ (도구, 부위) 일거리 19개를 일꾼 8명이 나눠 돌린다(`tools/run_metrics.py`).
- 서비스 코드(`ai/app`)는 고치지 않았다.
- 이 개발 PC(Intel Core Ultra 9 185H, 논리 코어 22개, RAM 63.5GB)에서 충전 상태로 잰 값이다.
- 작업 계획에 적은 「자동 튜닝 한 번 도는 시간」은 튜닝 도구가 S15P31A306-343에서 생기므로, 같은 일인 「기준값 하나 바꿔 다시 재는 시간」(빠른 판)으로 대신 쟀다.
- 지표 도구 최신판(S15P31A306-331)과 지도 다시 쓰기(S15P31A306-333)가 병합되기 전에 둘을 합친 위에서 작업하고 쟀다. 두 작업이 병합된 뒤 이 작업의 커밋만 master 위로 옮겼고, 바꾼 내용은 옮기기 전과 같다. 그 사이 master에 들어온 변경은 가이드 영역·지표 도구 코드를 건드리지 않아 위 측정 값은 그대로다.

## 재는 방법

### 도구

`tools/profile_metrics.py`는 지표 도구 main을 그대로 부르면서 사진 읽기·가림 표 읽기·얼굴 지도 펴기·가린 칸 지도 펴기·중앙값 지도·분할 모델·나가는 영역 만들기·저장 읽기·쓰기와 부위별 재기 함수를 시계로 감싼 판으로 잠깐 바꿔 끼운다. 지표 도구 코드는 고치지 않는다. 구간마다 호출 수, 서로 다른 사진 수, 자체 시간을 적고, 0.2초마다 메모리를 재며, 시작·끝의 전원 연결 여부를 적는다. 결과는 도구 결과 옆 `profile_<도구>.json`이다. 시계는 S15P31A306-333의 `tools/profile_guide_area.py` Recorder를 그대로 쓴다.

일꾼 여럿으로 돌릴 때는 `tools/run_metrics.py`가 일거리마다 걸린 시간과 전체 시간을 `run_metrics.json`에 적고, 메모리는 python 프로세스 메모리 합을 2초마다 따로 쟀다.

## 도구끼리 같이 쓰는 저장

### 무엇을 저장하나

| 저장 | 내용 | 위치 |
| --- | --- | --- |
| 사진 지도 | 사진마다 (얼굴 지도, 가린 칸 지도), 압축 없는 npz 하나 | `samples/<영상>/output/cache/face_maps/<가림 표 이름>/<사진 번호>.npz` |
| 대표 지도 | 사진 묶음·범위마다 (지도, 모름 칸) | `samples/<영상>/output/cache/median_maps/<가림 표 이름>/<지문>.npz` |
| 대표 지도 기억 (메모리) | 잡음 도구가 도는 동안 (부위, 쪽, 사진 묶음)으로 낸 지도 최근 512개 (`RememberedMedians`) | 메모리 |

- 디스크 읽기·쓰기는 한 장에 약 3ms로, 새로 펴는 약 250ms보다 약 80배 싸다. 압축(`savez_compressed`)하면 쓰기가 약 120ms로 느려져 압축하지 않았다.
- 잡음 도구 요청을 사진 없이 실제 코드 그대로 따라 세어 보니 중앙값 3,532번·서로 다른 사진 2,733장·지도 펴기 7,660번이 처음 상태 측정과 정확히 같았다. 그중 서로 다른 중앙값은 2,130번(61%)이고, 같은 묶음을 다시 쓰기까지 사이에 낸 대표 지도는 최대 400개라 기억을 512개로 정했다.
- 네 도구가 펴는 사진은 합치면 약 3,600장인데 따로 돌면 약 6,000장을 폈다.
- 사진 지도 저장은 `tools/face_map_store.py`의 `StoredPhotos`가 맡는다. 서비스 `RememberedPhotos`를 이어받아 「메모리 → 디스크 → 새로 펴기」 순서로 지도를 얻고, 서비스의 `rows_to_known_map`은 꾸러미로 알아보고 그대로 부른다.
- 여러 일꾼이 같은 파일을 동시에 써도 반쯤 쓴 파일을 읽지 않게 임시 이름으로 쓴 뒤 이름을 바꾼다. 윈도우에서는 다른 일꾼이 그 파일을 읽는 중이면 이름 바꾸기가 거절되므로(`PermissionError`) 0.05초씩 쉬며 다섯 번까지 해 보고, 그래도 안 되면 저장만 건너뛴다. 꺼낼 때 지문을 보므로 결과는 그대로다. 깨진 파일은 다시 펴서 덮어쓴다.

### 낡은 저장을 거르는 지문

| 저장 | 지문에 넣은 것 |
| --- | --- |
| 사진 지도 | 사진 파일 크기·수정 시각, 그 사진의 얼굴 점, 가림 표 파일 크기·수정 시각, 지도 펴기 코드(`face_map.py`, 얼굴 지도 자료 triangles·uv, 사진 읽기 `reference_input.py`, `make_face_maps`) |
| 대표 지도 | 묶음 속 사진마다의 위 지문, 볼 범위 값, 대표 지도 코드(`area_preparation.py`·`face_map.py`)와 상수 `OCCLUSION_MARGIN_CELLS`·`OCCLUDED_MAX`의 지금 값, 가림 여부 |

판정 기준값은 대표 지도 지문에 넣지 않는다. 그래서 기준값만 바꿔 다시 재면 같은 대표 지도를 꺼내 쓰고, 범위 넓힘이나 대표 지도 상수가 바뀌면 다른 이름이 되어 새로 만든다. 사진 내용 전체를 해시하는 방법은 실행마다 사진 603MB를 다시 읽어야 해서 쓰지 않았다.

### 효과 (작은 입력)

| 상태 | 합계 | 전 대비 |
| --- | --- | --- |
| 사진 지도 저장 + 잡음 대표 지도 기억, 저장이 빈 첫 실행 | 17분 21초 | −47% |
| 같은 코드, 다음 실행 (사진 펴기 0) | 12분 52초 | −61% |
| 대표 지도 저장까지, 대표 지도 저장이 빈 첫 실행 (사진 지도 저장은 찬 상태) | 11분 0초 | −66% |
| 대표 지도 저장까지, 다음 실행 (펴기·대표 지도 만들기 0) | 4분 56초 | −85% |

모든 실행에서 결과가 바이트까지 같다. 대표 지도까지 저장한 다음 실행은 사진 지도를 메모리에 올릴 일이 없어 메모리도 줄었다(잡음 4.6 → 2.7GB, 나머지 약 1GB). 남은 시간은 대표 지도 만들기(사진 지도 저장만 있을 때 다음 실행 772초 중 약 457초)가 빠진 나머지, 곧 부위마다의 계산이다.

## 빠른 판: 기준값만 바꿔 다시 재기

### 서비스 찾기 안의 대표 지도

안정성·경계 도구의 대표 지도는 서비스 부위 찾기 함수 안에서 만들어진다. 다섯 부위 파일(`brow_area`·`eyeshadow_area`·`eyeliner_area`·`blush_area`·`lip_area`)이 모두 `rows_to_known_map`이라는 이름으로 대표 지도를 만들어, 도구가 시작할 때 그 이름 자리를 저장 판(`stored_rows_to_known_map`)으로 바꿔 끼운다(`install_stored_medians`). 서비스 코드는 그대로이고 이 프로세스 안에서만 바뀐다. 저장을 쓰지 않는 꾸러미로 부르면 원래 함수와 같다. 서비스 파일에 갈림길을 넣는 방법은 서비스 리뷰 범위가 커지고 S15P31A306-333이 고친 파일이라 쓰지 않았다.

### `--set`·`--tag`와 실행기

```
uv run python tools/run_metric.py <도구> <샘플 폴더> [도구 인자...] --set eyeshadow_area.REDDENING_MIN=1.2 --tag shadow12
```

- `--set <모듈>.<상수>=<값>`은 서비스 부위 코드의 상수를 바꾼다. 모든 값을 먼저 검사하고 다 맞으면 한꺼번에 바꾼다. 숫자 상수는 정수·소수를 모두 받는다(섀도 `REDDENING_MIN`이 코드에 정수 1로 적혀 있어 1.2로 바꿔 볼 수 있게).
- 잡음·색 변화 도구는 불러올 때 일부 상수를 부위 표(`PARTS`)에 복사한다. 그래서 `--set`은 도구 안이 아니라 상수를 먼저 바꾸고 그다음 도구를 불러오는 `tools/run_metric.py`와 `tools/profile_metrics.py`에서 받는다.
- `--tag <이름>`은 결과를 `<가림 표 폴더>/<이름>/`에 따로 두고 바꾼 상수를 `settings.json`에 적는다. `--set`만 주면 기준 결과를 덮지 않게 거절한다.

### 확인 (작은 입력, 섀도 `REDDENING_MIN` 1 → 1.2)

- 대표 지도 만들기 0번, 사진 펴기 0번으로 도구 넷 5분 1초, 판정 2초에 끝났다.
- 섀도 줄만 달라졌다(잡음 80줄 중 79, 안정성 2줄 모두). 다른 부위는 바이트까지 같다. 잡음 결과의 섀도 기준값 칸이 1.2로 적혀 도구가 복사한 값까지 바뀐 것을 확인했다.
- 색 변화·경계 도구의 섀도 줄은 같았다. 작은 입력의 섀도 단계(s17)가 원래 찾음 문턱(`FOUND_TOP_MIN`)에서 못 찾음이라 1.2여도 못 찾음이다.

1.2는 빠른 판이 맞게 동작하는지 보려고 고른 시험값이고, 기준값을 정한 것이 아니다.

## 나눠 돌리기

지금 남은 시간은 부위마다 한 번은 해야 하는 계산(바뀐 색 계산·판정·나가는 영역)이라 저장으로는 줄지 않는다. 부위끼리는 서로의 결과를 쓰지 않으므로 나눠 돌릴 수 있다.

### 일거리 줄

`tools/run_metrics.py`가 (도구, 부위) 일거리 19개를 긴 도구부터(잡음 → 색 변화 → 안정성 → 경계, 도구 안은 부위 순서) 줄 세우고 일꾼 N명에게 나눠 준다. 일거리마다 `run_metric.py`를 따로 띄워 그 부위만(`--parts`) 계산해 임시 폴더에 쓰게 하고, 다 끝나면 도구마다 부위 순서대로 이어 붙여(`merge_results`) 네 도구를 다 합친 뒤 한꺼번에 결과 파일을 쓰고 판정 도구를 돌린다. 네 도구의 결과 쓰기를 한 형식(`write_result`)으로 모아 이어 붙인 파일도 같은 바이트가 된다. 일거리가 하나라도 실패하거나 합치다 멈추면 어느 도구 결과도 쓰지 않는다(앞 도구만 새 결과인 섞인 폴더가 남지 않게). `--tools`로 일부 도구만 돌리면 판정 도구는 돌리지 않는다. 폴더에 남은 다른 도구의 옛 결과(다른 기준값으로 만들었을 수도 있다)와 섞어 판정하면 완성된 판정처럼 보이기 때문이다. 도구마다 일꾼 풀을 두는 방법은 전체 일꾼 수를 하나로 다루기 어려워 쓰지 않았다.

경계 도구의 분할 모델(BiSeNet, onnxruntime)은 혼자서도 코어를 7~14개 써서 다른 일꾼과 다툰다. 경계 도구에 `--ort-threads`를 두고 실행기는 1개를 넘긴다. 1개여도 결과가 바이트까지 같았다.

## 실행 방법

ai/ 폴더에서.

```
uv run python tools/run_metrics.py samples/local_03_seq --model <resnet18.onnx> --occlusion <가림 표 이름>
uv run python tools/run_metrics.py samples/local_03_seq --model <resnet18.onnx> --occlusion <가림 표 이름> --set eyeshadow_area.REDDENING_MIN=1.2 --tag shadow12
```

| 옵션 | 뜻 |
| --- | --- |
| `--workers <수>` | 일꾼 수. 기본 8 |
| `--ort-threads <수>` | 경계 분할 모델 코어 수. 기본 1 |
| `--tools <도구,도구>` | 일부 도구만. 이때는 판정 도구를 돌리지 않는다 |
| `--no-store` | 디스크 저장을 쓰지 않는다(메모리 기억만) |
| `--set`·`--tag` | 빠른 판. `--set`을 주면 `--tag`도 줘야 한다 |

- 도구 하나만 돌리려면 지금처럼 `tools/noise_metric.py` 등을 직접 부르고, 그 부위만 돌리려면 `--parts`를 준다. 기준값을 바꾸려면 `tools/run_metric.py`로 부른다.
- 구간별 시간을 재려면 `tools/profile_metrics.py <도구> <샘플 폴더> [도구 인자...]`.
- 이 문서의 측정 결과는 git에서 무시되는 폴더에 있다. 시험 영상 전체는 `ai/samples/local_03_seq/output/occlusion/`의 `before334/`(전, 구간 기록 포함), `after334/first/`(첫 실행), `after334/`(다음 실행), `after334/shadow12/`(빠른 판)이다. 작은 입력은 저장소 밖 샘플 폴더의 같은 이름 아래에 있다.
- 저장은 `samples/<영상>/output/cache/` 아래에 있고 git에서 무시된다. 시험 영상 전체가 약 24GB다. 지워도 다음 실행에서 다시 만들어지므로 공간이 필요하면 폴더째 지우면 된다. 사진·얼굴 점·가림 표·지도 펴기 코드가 바뀌면 지문으로 알아보고 그 사진·묶음만 다시 만든다.

## 한계

- **잡음 눈썹 일거리 하나가 병목이다.** 시험 영상 전체에서 그 일거리 하나가 첫 실행 884초, 다음 실행 400초, 빠른 판 362초로 전체 시간과 거의 같다(눈썹의 안 건드린 구간이 가장 길다). 일꾼을 늘려도 줄지 않는다. 잡음 일거리를 구간·간격별로 더 쪼개면 다음 실행을 2~3분대로 줄일 수 있다고 어림하지만 재 보지 않았다.
- **메모리:** 일꾼 8명이 각자 사진 판정 결과(얼굴 점)를 읽어 시험 영상 전체에서 최대 33.8GB를 썼다. RAM이 작은 컴퓨터에서는 `--workers`를 줄여야 한다. 기준값 튜닝에서 시도 여러 개를 동시에 돌리면 그만큼 더 든다.
- **디스크:** 시험 영상 전체 저장이 약 24GB다.
- **지문의 빈틈:** 사진·가림 표는 파일 크기와 수정 시각으로 알아본다. 내용이 바뀌었는데 크기와 수정 시각이 그대로면 옛 저장을 쓴다(사진을 다시 뽑으면 수정 시각이 바뀐다).
- **분할 모델 1코어:** 결과가 같은 것은 이 PC와 이 모델 파일(`resnet18.onnx`)에서 확인한 것이다.
- 일꾼 수와 시간은 이 개발 PC 값이다. 운영 서버에서는 지표 도구를 돌리지 않는다.
