2026-11-09 · S15P31A306-417

## 요약

### FE로 가는 영역 형식

BE는 저장한 영역을 튜토리얼 조회(`GET /api/v1/guides/{guideId}`)에서 `shared/guide-area`의 하위 단계(`subSteps`) 그대로 FE에 넘긴다. 예전 명세의 `application`(`face_template_v1`)과 그 좌우 칸 `side`는 BE·FE 모두 쓰지 않고, 좌우는 부위 이름(`leftEye` · `rightEye` 등)으로 FE가 판단한다([api-spec.md](../references/api-spec.md) 「가이드 조회」, `frontend/docs/API_CHECK.md`). 짝 부위와 가운데 부위가 한 단계에 섞여도 BE에 따로 요청할 형식 차이는 없다.

### 사진 뽑는 규칙

AI가 받는 사진은 BE 쪽에서 영상에서 뽑는다. 뽑는 곳이 두 곳이고 규칙이 다르다.

| | BE worker([`FramePlan.java`](../../backend/src/main/java/com/mairor/backend/analysis/frames/FramePlan.java)) | 노트북 처리기([`video-processor/pipeline.py`](../../video-processor/pipeline.py)) |
| --- | --- | --- |
| 쓰는 때 | 운영자가 올린 영상으로 분석할 때. 11-04 · 11-06 실행 | YouTube 영상을 노트북이 받아 처리할 때(S15P31A306-357). AI로 넘기는 연결(S15P31A306-358)은 아직 master에 없고, 연결 설정 `ANALYSIS_PROCESSOR_ENABLED`는 기본 꺼짐 |
| 뽑는 범위 | 영상 전체 | 바르는 단계(`isCosmeticApplication`) 구간 안과 첫 단계 앞 10초 |
| 기본 간격 | 초당 약 2장 | 초당 1장 |
| 단계 시작·끝 앞뒤 3초 | 초당 약 10장 | 따로 없음 |

AI 영역 분석은 분석하는 단계의 시작 직전 창과 끝 직후 창 사진만 비교하고, 사진 판정은 앞뒤 1초 사진과 얼굴 크기를 견준다([`reference_area.py`](../../ai/app/tasks/area/reference_area.py) `PART_WINDOWS` · `photo_ranges`).

| 부위 | 직전 창 | 직후 창 |
| --- | --- | --- |
| 립 | - | 1초 |
| 블러셔 | 1초 | 1초 |
| 눈썹 | 1초 | 2초 |
| 섀도 | 2초 | 1초 |
| 아이라인 | 1초 | 3초 |

- BE worker 규칙이면 창마다 사진이 10~30장 들어온다. 11-04(8,109장) · 11-06(7,373장)은 이 규칙이다. 노트북 규칙이면 31분 영상이 많아야 1,858장이다.
- 노트북 규칙이면 창마다 0~3장이다. 직전 창은 앞 단계가 바르는 단계로 바로 붙어 있을 때만, 직후 창은 다음 단계가 바르는 단계일 때만 사진이 있다. 「쓸 사진 없음」으로 기본 가이드가 되는 단계가 늘 수 있다.

### 가림 찾기

가림 찾기(손·붓·자막이 가린 칸을 찾는 모델)는 운영 기록에 따로 구간이 없어 부위별 영역 찾기 안에 섞여 있다. 같은 코드를 서버 흉내(코어 2개)로 잰 S15P31A306-333 기록에서는 영역 만들기의 약 4분의 1이다.

| 조건 | 영역 만들기 | 가림 찾기 | 사진 한 장 |
| --- | --- | --- | --- |
| 333 병합 전 코드, 서버 흉내 | 511.2초 | 130.4초(26%), 552장 | 0.24초 |
| 333 병합 뒤 코드, 서버 흉내(두 줄) | 274.0초 | 205.2초(두 줄이 동시에 쓴 시간의 합이라 벽시계 시간보다 크다) | 0.39초 |
| 가림 실험 문서 기준(22코어) | 260초 | 22.1초 | |

- 코어 수에 따라 크게 달라진다. 22코어에서 22초인 것이 코어 2개에서는 130초다.
- 운영 11-06 영역 찾기 341.4초에 333 병합 전 비율(26%)을 대면 약 87초다(어림).
- BE 설정(콜백 대기, 진행률)에는 영역 시간 전체를 쓰므로 이 값만 따로 운영에서 잴 필요는 없다. 가림 찾기만의 운영 값이 필요하면 서비스에 구간을 더해야 한다.

### 얼굴 점 찾기 방식(IMAGE · VIDEO)

서비스는 MediaPipe 얼굴 점 모델을 사진마다 따로 보는 IMAGE 모드로 쓴다([`face_finder.py`](../../ai/app/tasks/area/landmarks/face_finder.py)). 앞 사진을 이어받아 추적하는 VIDEO 모드가 더 빠른지, 같은 점을 내는지 견주었다. 시험 영상에서 서비스가 영역에 쓰는 사진 1,376장을 시간 순으로 넣고, 이 컴퓨터를 코어 2개로 묶어 모델 호출 시간만 쟀다(사진 읽기 제외). IMAGE → VIDEO → IMAGE 순서로 돌렸다.

| | IMAGE | VIDEO | IMAGE(다시) |
| --- | --- | --- | --- |
| 1,376장 모델 시간 | 12.6초 | 12.0초 | 12.2초 |
| 한 장 가운데 값 | 9.0ms | 8.6ms | 8.7ms |
| 얼굴 찾은 사진 | 1,339 | 1,339 | 1,339 |
| IMAGE와 점 차이 | | 0 | 0 |

- VIDEO는 IMAGE와 같은 사진에서 얼굴을 찾고, 점 위치도 같다.
- 시간 차이(4%)는 IMAGE를 두 번 잰 차이(3%)와 비슷해 의미 있게 빠르지 않다.
- 얼굴 점 구간에서는 모델보다 사진 읽기가 더 크다(333 기록, 서버 흉내: 사진 읽기 18.9초, 모델 15.9초).
- 그래서 IMAGE 모드를 그대로 둔다.

### S15P31A306-333 병합 뒤

333은 영역에 쓰는 사진만 받고(시험 영상 6,477 → 1,376장), 같은 사진을 얼굴 지도에 한 번만 펴고, 영역 찾기를 두 줄로 나눠 서버 흉내 기준 전체 시간을 58% 줄였다(812.3초 → 344.7초). 11-09 19:27 master에 병합돼 운영에 배포됐고, 배포 뒤 운영 실행 기록은 아직 없다.

| --- | --- | --- |

어림은 11-06 시간에 서버 흉내의 줄어든 비율(0.42)을 곱한 값이다. 서버 흉내가 운영보다 느리게 나오는 구간이 있어 실제와 다를 수 있다. 사진을 덜 받으면 얼굴 점·판정의 비중이 줄고 영역 찾기의 비중이 커진다(서버 흉내 병합 뒤 영역 찾기 79%).

## 발견한 것

- **지금 공개 튜토리얼은 옛 코드 결과다.** BE는 영상마다 공개 가이드를 하나 두는데, 이 시험 영상은 11-04 결과가 승인돼 있다. 그래서 마스카라 단계가 기본 가이드(`template`) 대신 `notApplicable`로 나간다. 지금 코드로 만든 11-06 결과는 검수 대기다.
- **노트북 처리기는 BE worker와 다른 규칙으로 사진을 뽑는다.** 바르는 단계 안에서만 초당 1장이고 단계 경계 앞뒤가 촘촘하지 않아, AI가 비교할 직전·직후 사진이 거의 없다. 노트북 결과를 AI로 넘기는 연결을 켜기 전에 규칙을 맞추도록 요청했다([요청 문서](../requests/2026-11-09-hyeonsoo-hyeongjun-processor-frame-rule.md)).
- **BE는 영역 안쪽을 실행 중에 검사하지 않는다.** 규칙이 바뀌기 전 결과(11-04)도 그대로 저장되고 승인될 수 있었다. AI는 결과를 만들 때 서비스 모델로 같은 규칙을 검사하므로 지금 코드에서는 어긋난 결과가 나가지 않는다. 운영에 나간 실제 결과는 `ops_guide_job_check.py`로 다시 확인할 수 있다.
